# 微语产品反馈与迭代清单

> 来源：用户整理的群聊讨论
>
> 更新日期：2026-08-25
>
> 这份清单记录真实讨论中反复出现的需求、质疑和风险。它是产品迭代台账，不把零散的审美评价或玩笑当成需求结论。
>
> **状态修订（2026-08-26）：** 事件识别、跨会话合并、证据绑定和最终展示尚未完成真实金标准与端到端验收。此前标记为完成的相关项只代表 legacy 局部字段或构造样本回归存在，现已重新开放。当前权威路线见 `docs/design-review.md` 第三版。

## 产品判断

- [x] 核心问题不是“告诉用户要看什么”，而是减少用户不得不看的无关信息。
- [x] 产品不能只做单段群聊压缩；差异点是跨群聊、私聊和其他来源追踪同一件事。
- [x] 过滤结果必须可解释、可回溯，避免把降噪做成新的信息茧房；当前输出噪音类型、原因、样本和原消息计数。
- [ ] 每条整理结果都要回答“看完之后怎么办”：状态、待确认问题、责任人、截止时间或下一步。
- [ ] 明确“群聊摘要”和“跨对话事项归档”的产品边界，避免用户把微语理解成普通日报工具。
- [ ] **局部实现，待重做。** legacy 事件结果能够输出聚类分数、合并依据、共享主题和证据绑定率，但这些字段没有阻止错误事件合并，也没有保证首页采用同一来源。第三版需输出稳定 ID、五分类事件关系、支持/冲突槽位、版本和 provenance，并通过最终 UI 验收。

## P0：风险与使用边界

- [x] 产品边界保持永久只读，不自动回复、不自动发送、不把发送列入未来规划。
- [x] README 已说明：只读不等于无风险，读取微信内部数据仍可能带来平台、账号、隐私和合规风险。
- [x] 在工作台同步入口展示低频同步提醒。
- [ ] 记录同步运行历史和失败原因，帮助用户判断是否需要重试，减少“连续点击试试看”。
- [ ] 区分“自动刷新本地工作台”和“主动发起历史同步”，避免用户误以为两者风险相同。
- [ ] 不把“每天 2–3 次”宣传为安全阈值；根据真实使用反馈和平台规则持续复核文案。

## P1：核心能力

- [ ] 以“事项 / 事件”而不是“消息条数”作为主要整理单位。
- [ ] 将多个会话中关于同一件事的消息合并成一条事件主线。
- [ ] 事件卡片至少包含：发生了什么、当前状态、参与人、已确认事实、未解决问题、下一步和证据链接。
- [ ] 支持从事件结论回到原始消息，并展示必要的前后文。
- [ ] 对被过滤内容提供范围、原因和回看入口，保留信息发散能力。
- [ ] 提供“与我相关”与“全局观察”两种视角，避免只按用户画像收窄信息。

## P1：准确度与可解释性

- [ ] 评估同一事件跨会话合并的准确率，重点监控错误合并和重要事项漏报。
- [ ] **局部实现，待金标准验证。** 已为只共享一个宽泛短语的 legacy 跨会话候选增加门槛和反向样例，但真实链路仍会把同属 AI 服务的不同对象、动作和诉求合并。第三版改用动作、核心对象、时间/状态、诉求硬门槛与五分类事件关系。
- [x] 对模糊上下文、不完整表达和群聊黑话先标记不确定性，不强行解释梗义；反讽仍需真实样本继续校准。
- [ ] **局部实现，待端到端验收。** legacy 输出保留了部分命中原因、证据编号和置信度，梗候选也保留重复消息与邻近回应，但人物—主张—对象关系、证据片段、稳定 ID、版本/provenance 和最终页面采用来源仍不完整。
- [ ] 将“重要性判断”和“事实识别”分开，避免把算法排序当成事实。
- [ ] 建立用户反馈闭环：有价值、误判、错误合并、漏掉重要事项。
- [x] 把“群聊梗蒸馏”作为独立质量目标评估，不与普通日报摘要混为一谈；当前只输出带证据的 `inside_joke` / `repeated_phrase` 候选。

## P1：噪声与身份

- [x] 算法第一版处理多话题并行、插话、寒暄、纯确认和情绪反应：短句保留作上下文，噪音分层收起，并阻断仅凭时间相邻的跨话题上下文串线。
- [ ] 提升群聊发言人识别和名称消歧，无法确认时明确显示待确认。
- [ ] 处理不同人对同一件事的不同说法，以及跨时间的上下文断裂。
- [ ] 让“噪声过滤”可配置，而不是用一套不可见的固定规则替用户决定。

## P2：来源与扩展

- [ ] 当前优先打磨群聊 + 私聊的跨会话事项追踪。
- [ ] 再评估会议录音：录音质量、转写错误、错别字纠正和发言人分离是独立问题。
- [ ] 将企业微信、飞书等平台作为后续合规和数据源评估方向，不在当前阶段同时铺开。
- [ ] 只有在基础准确度达标后，再扩展图片 OCR、语音转写和复杂多模态归档。

## 需要继续验证的问题

- [ ] 用户看完一条事件归档后最希望直接完成什么动作？
- [ ] 用户更需要“低频主动同步”还是“后台持续接收、定时整理”？
- [ ] 哪些遗漏比哪些误报更难接受？
- [ ] 用户愿意为跨会话归档提供哪些主题、联系人或项目画像？
- [ ] 群聊中的梗、情绪和关系变化是否是独立的高价值场景？
- [ ] 个人微信、企业微信和飞书分别适合怎样的只读数据接入方式？

## 2026-08-25 拟真审核结论

> 历史样本说明：以下数字只描述当时 52 条构造消息上的 legacy 行为，结论已经降级，不能作为真实数据准确率、事件识别完成度或生产验收依据。

- 使用 52 条混合消息、6 个会话和人工预期标签做端到端审核，覆盖项目反馈、并行话题、跨会话风控、社交闲聊、任务重复、反应消息、媒体占位符和梗变体。
- 硬噪音识别：precision 1.000、recall 1.000；7 条应收起消息没有进入价值面，原始消息计数仍保持完整。
- 梗候选识别：`未来古法` 的两次出现和两条邻近反应被识别为 `inside_joke`；precision 1.000、recall 1.000。重复确认语和重复报价请求没有被当成梗。
- 第一屏聚焦面：precision 1.000、recall 0.780；完整编辑面：precision 0.911、recall 1.000。前者更适合减少注意力消耗，后者保留低优先级事项供回看。
- 并行话题审核中，固定样本里的模型部署与选课没有合并；同一类风控证据由两张重复事件卡合并为一条跨会话证据链。该结果没有覆盖 GPT 重置、中转站、multica 消耗等“同父主题、不同事件”难负例。
- 以上是拟真审核，不等于真实微信历史数据上的准确率；下一步必须用脱敏真实样本做人工标注，并记录“有价值 / 误报 / 错误合并 / 漏报 / 梗义不确定”等反馈。
