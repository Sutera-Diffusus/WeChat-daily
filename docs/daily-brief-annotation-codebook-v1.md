# 微信日报 ACU 标注规范 v1

## 1. 标注目的

本规范服务于“每日微信记录中哪些信息值得进入用户日报”的研究评估。标注对象是 Atomic Content Unit（ACU），不是消息、会话、主题标签或最终文案。

ACU 必须满足：

- 只表达一个可独立判断真伪或状态的意义；
- 能绑定到一条或多条直接证据消息；
- 人物、动作、对象和状态能够分别记录；
- 与其他 ACU 合并后不会丢失独立判断边界。

## 2. 标注单位

### 2.1 应拆分

一句话同时包含两个可独立变化时拆开。例如：

- “课程改到周六，并要求填写问卷”拆成“课程日期变化”和“需要填写问卷”。
- “甲申请退出，老师尚未回复”拆成“甲提交申请”和“批准状态未知”。

### 2.2 应合并

多条消息共同表达同一个状态时合并。例如：

- 两人分别反馈同一服务在相近时间不可用，可形成一个“多人报告可用性异常”的 ACU，但不能升级为“服务发生全局故障”。
- 同一交接过程中的材料请求、文件发送和收件确认，可分别形成过程 ACU；若最终只关心是否闭环，可增加一个由这些证据共同支持的状态 ACU。

### 2.3 不标为 ACU

- 纯表情、寒暄、无对象短句；
- 只能依赖图片内容但图片不可读；
- 与上下文无法建立可靠指代关系的“这个好了”“搞定了”；
- 没有信息增量的重复转述；
- 仅由摘要模型推断、原消息不能直接支持的结论。

## 3. 字段定义

每条 JSONL 记录包含：

```json
{
  "acu_id": "acu-YYYYMMDD-NNN",
  "date": "YYYY-MM-DD",
  "atomic_content": "一个原子意义",
  "evidence_message_ids": ["source-message-id"],
  "context_message_ids": [],
  "actor": "人物、组织或 unknown",
  "action": "动作、陈述、决定、状态变化或 unknown",
  "object_or_recipient": "动作对象、接收者或 unknown",
  "status": "confirmed|reported|pending|rejected|resolved|unknown",
  "claim_type": "observed_action|reported_experience|opinion|question|hypothesis|resource",
  "user_relevance": "direct|decision_support|situational_awareness|background|none",
  "inclusion_label": "must|may|exclude",
  "exclusion_reason": null,
  "uncertainty": [],
  "annotator_note": ""
}
```

### 3.1 actor

执行动作、作出决定或发表主张的人/组织。不能把聊天对象自动视为 actor，也不能根据人称语气覆盖消息方向元数据。元数据与语义冲突时填 `unknown`，在 `uncertainty` 中记录冲突。

### 3.2 object_or_recipient

动作作用的对象或接收者。双向协作且方向无法可靠区分时，使用中性联合对象，例如“用户与宁江月之间的团组织关系转接工作交接”，不要强行指定交出方和接收方。

### 3.3 status

- `confirmed`：原消息直接确认动作、决定或状态；
- `reported`：只能确认某人这样陈述或体验；
- `pending`：申请、等待回复或未闭环；
- `rejected`：明确否决或取消；
- `resolved`：明确完成且后续无需处理；
- `unknown`：现有证据无法确定。

沉默、话题结束或没有后续消息不等于 `resolved`。

### 3.4 user_relevance

- `direct`：直接改变用户需要做的事或当前状态；
- `decision_support`：能够影响用户的选择或判断；
- `situational_awareness`：值得知道的外部变化或群体信号；
- `background`：有内容但对当前用户价值较弱；
- `none`：不构成用户日报价值。

“私聊”“提到用户”“用户自己发言”不是 `direct` 的充分条件。

## 4. 纳入标签

### 4.1 must

若遗漏会实质性降低用户对当天重要变化、决定、风险或可用知识的理解。

常见依据：

- 明确改变用户的行动或决定；
- 有重要状态变化、结果、阻断或确认；
- 对用户正在进行的项目提供关键判断依据；
- 多条可靠证据共同形成非显然的新信息。

### 4.2 may

有一定价值，但是否纳入取决于当天整体信息、用户兴趣或报告篇幅；遗漏不会造成明显误判。

### 4.3 exclude

不应进入主报告。必须填写 `exclusion_reason`：

- `trivial`：日常琐事或低影响行政细节；
- `duplicate`：没有新的意义；
- `no_change`：只有背景或重复观点，没有当天变化；
- `unresolved_reference`：主体、对象或指代无法确认；
- `unsupported`：内容不能由直接证据支持；
- `private_low_utility`：私密且对日报价值低；
- `off_topic_for_user`：有内容但与用户日报目标无关；
- `pure_question`：只有问题且没有答案、决定、风险或可执行核查价值；
- `social_chatter`：寒暄、情绪、玩笑或梗；
- `unavailable_media`：关键含义只在不可用媒体中。

## 5. 关系与归因标注

### 5.1 权威顺序

1. 明确回复/引用关系；
2. 完整连续对话中的人称与动作；
3. 消息方向和 sender 元数据；
4. 单句语气推断。

不同来源冲突时不做多数投票，标记 `unknown` 并保留冲突证据。

### 5.2 禁止推断

- “没有后续”不能推断“已完成”；
- “转给你”不能脱离前后轮次推断具体交接方向；
- 群友说“会风控”不能写成平台规则；
- 两人报告不可用不能写成全局服务故障；
- 用户表达偏好不能写成产品客观优劣。

## 6. 双重标注与仲裁

同一日期至少进行两次相互独立的标注：

1. 第一次只看原消息和交流过程，不看旧日报；
2. 第二次可查看旧日报，但必须独立填写 ACU；
3. 比较 ACU 对齐、纳入标签、人物槽位和证据绑定；
4. 分歧进入仲裁记录，不直接覆盖任一版本。

在单用户研究中，两次标注可以由同一用户/专家在不同时间完成，但必须保留轮次和时间，避免把一次判断当作绝对金标准。

## 7. 一致性检查

自动检查：

- `acu_id` 唯一；
- `must|may` 至少有一条直接证据；
- `exclude` 必须有排除原因；
- evidence ID 必须存在于当天数据库；
- `pending|unknown` 不得被摘要改写为完成；
- actor/object 冲突项必须包含 uncertainty；
- 同一证据可以支持多个不同 ACU，但同一 ACU 不得重复绑定同一证据。

人工检查：

- 原子性；
- 人物和方向；
- 是否把群体观点升级成事实；
- 是否因私聊、@用户或硬日期而机械提高重要性；
- 是否漏掉跨多条消息形成的真正变化。

## 8. 标注输出不等于生产逻辑

ACU 金标准用于测量和比较方案。它不规定生产系统必须增加对应模块，也不意味着标注字段都要在运行时生成。只有消融和盲测证明某类结构能稳定改善结果，才考虑接入现有实现。
