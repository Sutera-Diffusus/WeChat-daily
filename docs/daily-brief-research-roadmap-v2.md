# 微信日报优化研究路线 v2

> 本文替代“先规定输出条数、再设计多层编辑器”的方案。目标是以可证伪假设、人工金标准、消融实验和盲测结果决定改动；在证据出现前，不增加生产链路复杂度。

## 1. 任务定义

输入是用户一天内跨私聊、群聊、媒体占位和系统消息的完整记录。输出不是一般聊天摘要，而是一个**面向用户的、证据可追溯的日级信息压缩结果**。

系统需要同时回答：

1. 当天有哪些真正的新信息、变化、决定、风险或可复用认识？
2. 哪些信息对用户有实际意义？
3. 谁对谁做了什么，状态是否已确认？
4. 每项结论由哪些原始消息支持？
5. 哪些内容不确定、只是观点或不值得占用阅读时间？

报告长度是上述目标的结果，不是预先设置的常数。信息稀少时可以很短；信息密集时可以更长。

## 2. 当前证据支持的诊断

2026-09-16 的现有实验显示：

- 3,925 条消息可被无模型重建为 417 个交流过程和 76 条交流流；说明基础重建能够显著减少孤立消息问题。
- 402 张交流卡中有 392 张完成语义内容线抽取，调用 444 次；说明“无法理解消息”不是唯一或主要瓶颈。
- 最终报告仍然琐碎，且出现宁江月交接关系表述错误；说明成功抽取内容线不等于成功选择摘要内容，也不保证人物归因正确。
- 旧式 `primary_insights` 存在家教信息与 AI 模型话题误聚合；说明宽泛词重合会污染跨消息聚合。
- 编辑压缩器面对的只是上游已经误选的少数卡片，`accepted_headline_count=0` 后又由本地回退候选生成报告；说明最终编辑器无法恢复上游已经丢失的主线。

因此，当前最值得检验的假设是：**主要瓶颈位于内容选择和人物归因，而不是报告排版，也不能仅靠增加模型调用或固定篇幅解决。**

这仍是假设，必须通过实验分解确认。

## 3. 理论依据

本项目可借鉴但不能直接照搬以下研究结论：

1. 长对话中的相关信息稀疏且依赖上下文，`retrieve/locate then summarize` 往往优于直接对整段长对话摘要。QMSum 将会议摘要定义为面向不同用户问题的 query-based summarization；长对话研究也发现 retrieve-then-summarize 表现最好。
2. 摘要内容选择不能只看文字重合。Pyramid Method 和后续 Atomic Content Units 都把摘要拆成可比较的原子信息单元，用于衡量“选中了哪些重要意义”，而不是句子像不像参考答案。
3. 对话摘要存在普通文档摘要没有的 speaker dynamics、turn-taking 和“谁说了什么”错误；现有通用指标经常掩盖这类错误。
4. 事实一致性、相关性、连贯性和流畅性是不同质量维度，不能混成一个总分；自动指标在多维质量上可能出现虚假相关。
5. 摘要是否有用应通过下游任务评估，而不仅是内部文本质量分数。

这些依据支持“先定位相关交流，再选择原子信息，再验证人物和证据，最后成稿”，但并不支持任意层数、固定条数或固定权重。

## 4. 研究问题与可证伪假设

### RQ1：主要损失发生在哪里？

- H1a：交流过程重建遗漏了关键上下文。
- H1b：关键内容已被重建和抽取，但在重要性选择中丢失。
- H1c：内容选择基本正确，但成稿发生了关系方向、事实或表达错误。

三者必须用 oracle 实验分开，不能靠阅读最终报告猜测。

### RQ2：用户条件是否必要？

- H2：使用用户当期目标和历史反馈进行 query-conditioned selection，比通用“今日热点”摘要更有用。

对照实验必须让两种方法读取同一批重建内容，仅改变是否提供用户查询/目标。

### RQ3：交流过程重建是否真的优于扁平输入？

- H3：基于交流过程的输入，在关键内容召回、人物归因和错误合并方面优于时间窗口或孤立消息输入。

如果盲测没有提升，就不应继续维护复杂重建逻辑。

### RQ4：结构化证据约束是否改善关系准确性？

- H4：在生成摘要前要求每个原子主张绑定 `actor-action-object/recipient-status` 和直接证据，可降低人物关系方向错误。

结构化槽位先作为实验和校验数据，不立即变成新的生产服务。

### RQ5：如何决定报告长度？

- H5：用经人工标注校准的“应纳入/不应纳入”决策，比固定 Top-K 或固定篇幅更符合用户效用。

输出条数由通过纳入判据的内容单元自然产生。若校准结果显示阈值随日期或主题漂移，再研究自适应方法；不预先发明停止公式。

## 5. 金标准：先标内容单元，不先写标准答案

### 5.1 标注对象

以完整日期为样本。对当天原始消息和重建交流过程，人工标注 Atomic Content Units（ACU）：每个单元只表达一个可判断的意义。

每个 ACU 至少包含：

- 原子内容；
- 直接证据消息；
- actor、action、object/recipient、status；
- `confirmed / reported / opinion / question / unknown`；
- 对用户的意义；
- `必须纳入 / 可以纳入 / 不应纳入`；
- 不应纳入的原因，如琐碎、重复、无新信息、关系不明、隐私或与用户无关。

### 5.2 不假设唯一正确摘要

Pyramid 方法指出，同一材料可以存在多份同样好的摘要。因此金标准不固定唯一文案，也不固定条数；它定义应该覆盖的意义单元及相对重要性。

### 5.3 数据划分

使用所有已有完整日期建立样本池，而不是只优化 9 月 16 日。日期按时间切分为开发、校准和盲测集合，避免同一讨论跨集合泄漏。

初期先标已有代表性日期（包括 9 月 7、8、16 日）用于完善标注规范；样本量继续增加，直到主要指标的 bootstrap 置信区间和错误类型分布趋于稳定。这里不预设一个“看起来够用”的日期数。

## 6. 瓶颈定位：三个 oracle 实验

### 6.1 Reconstruction Oracle

人工给出正确的交流边界和必要上下文，让现有选择/成稿模块处理。

- 若质量显著提高，瓶颈在重建。
- 若没有，提高重建复杂度没有依据。

### 6.2 Selection Oracle

人工给出必须纳入的 ACU，让现有成稿模块生成报告。

- 若关系、事实和可读性仍错误，瓶颈在归因或生成。
- 若报告明显改善，主要瓶颈在内容选择。

### 6.3 Generation Oracle

保留系统选出的 ACU，由人工只负责忠实改写，不改变选择。

- 若仍然琐碎，证明选择错了。
- 若人工成稿良好而模型成稿差，才有理由修改生成提示或模型。

Oracle 实验的价值在于给每个阶段估计上限，避免数周继续优化错误组件。

## 7. 最小对照实验

只比较能回答研究问题的少量系统：

### B0：当前系统

现有规则基线、内容抽取、编辑压缩和 fallback，作为冻结基线。

### B1：扁平 Query Baseline

不做复杂过程重建；按聊天和时间保留消息，让模型围绕固定用户问题定位证据并摘要。用于检验现有重建是否真的产生价值。

### B2：现有重建 + Query-conditioned Selection

保留当前交流过程重建与内容线抽取，只替换选择目标：从“这张卡重要吗”改为“该内容是否回答用户日报问题”。这是优先考虑的最小改动。

### B3：B2 + 结构化归因校验

在 B2 基础上增加 actor/action/object/status 的生成前校验。它只在 H4 得到支持后进入正式方案。

不同时引入新的聚类器、评分公式、编辑层和界面。每次实验只改变一个因素。

## 8. 评估指标

### 8.1 内容选择

- **ACU Recall**：必须纳入的原子内容有多少被报告覆盖。
- **ACU Precision**：报告中的内容有多少属于必须或可以纳入。
- **Weighted ACU Coverage**：按人工重要性加权的覆盖率，借鉴 Pyramid，而不是按消息数量加权。
- **Trivial Inclusion Rate**：不应纳入内容进入正文的比例。
- **Redundancy Rate**：同一 ACU 被重复表达的比例。

### 8.2 人物与状态

- actor、action、object/recipient、status 分槽准确率；
- 关系方向错误率；
- 对 `unknown` 应保持未知却被强行确定的比例；
- speaker attribution 错误单独报告，不并入文风分数。

### 8.3 证据与事实

- 每个报告主张的直接证据覆盖率；
- evidence precision：绑定消息是否真的支持该主张；
- unsupported claim rate；
- 外部事实是否正确标为“未核验”。

QA/NLI 类指标可作为诊断信号，但不能替代人工核验。研究表明不同自动指标会掩盖不同类型的摘要错误。

### 8.4 用户效用

采用任务型评估，而不是只问“看起来好吗”：

- 用户能否根据报告正确回答“今天发生了什么变化”；
- 能否识别需要处理和无需处理的事项；
- 找到证据或原聊天所需时间；
- 与基线报告成对比较时更愿意保留哪一份；
- 错误造成的实际成本，如误解交接方向或遗漏重要变化。

### 8.5 语言质量

相关性、一致性、连贯性、流畅性分别报告，不求一个总分。它们是成稿质量，不得代替内容选择和人物准确性。

## 9. 错误分类表

每次失败必须归入可行动类别：

| 编号 | 错误 | 示例 |
| --- | --- | --- |
| E1 | 交流边界错误 | 两个话题被切成一个过程或一个过程被拆散 |
| E2 | 说话者/主体错误 | 把用户说的话归给联系人 |
| E3 | 关系方向错误 | 把双向交接写成某人单向转交 |
| E4 | 对象污染 | 家教广告混入 AI 模型主题 |
| E5 | 重要内容漏选 | 高价值主线已抽取但未进入报告 |
| E6 | 琐碎内容误选 | 人员名单或普通提醒进入主正文 |
| E7 | 无证据结论 | 把群友体验写成平台事实 |
| E8 | 重复与冗余 | 同一事项被拆成多条 |
| E9 | 隐私边界错误 | 不必要的个人信息进入可转发正文 |
| E10 | 表达质量 | 内容正确但结构、语言或顺序不可读 |

每轮优化前先统计错误分布，只修复占主导且影响大的错误类型。

## 10. 决策规则

一个改动只有同时满足以下条件才进入主链路：

1. 在时间隔离的盲测日期上改善目标指标；
2. bootstrap 置信区间或逐日结果显示改善不是由单日样例驱动；
3. 不恶化关系方向、证据忠实和隐私三个底线指标；
4. 消融实验能把改善归因到该改动，而不是同时变化的提示词、模型或样本；
5. 改善幅度足以抵偿新的运行成本和维护复杂度。

若复杂方法没有显著胜过 B1 扁平基线，选择更简单的方法。

## 11. 实施顺序

### 阶段 A：冻结与复现

- 冻结当前 9 月 7、8、16 日输入、输出、配置和失败报告。
- 保证同一输入可重放，避免模型、提示、候选上限同时变化。

### 阶段 B：标注规范与一致性

- 用少量日期试标 ACU、人物槽位和纳入判断。
- 对同一日期独立标两次，检查自洽性；规范不稳定时先修标注定义，不训练选择器。

### 阶段 C：瓶颈定位

- 完成三个 oracle 实验。
- 量化重建、选择、归因和生成各自造成的损失。

### 阶段 D：最小实验

- 运行 B0-B2；只有归因仍是主要问题时再运行 B3。
- 记录每种方法的质量、调用次数、延迟和失败率。

### 阶段 E：盲测与决定

- 在未用于调试的日期上评估。
- 依据预先定义的指标决定保留、回滚或继续研究。

### 阶段 F：生产化

- 只把胜出的最小改动接回现有管线。
- 失败时显式标记无合格结果，禁止旧 fallback 冒充正式日报。

## 12. 对 9 月 16 日的正确使用

9 月 16 日不再被当作“必须马上排出一份漂亮日报”的单点任务，而是第一份系统错误分析样例：

- 宁江月用于 E2/E3；
- 家教信息混入模型话题用于 E4；
- 人员参会名单和维修提醒用于 E6；
- 群友模型体验被事实化用于 E7；
- 多条相关 AI 讨论是否形成真正主线用于 E5/E8。

先产出该日期的人工 ACU 金标准和错误账本，再用 Selection Oracle 判断：如果给定正确内容，现有成稿能否生成合格日报。这个结果将决定下一步是修选择还是修生成，而不是继续同时改所有模块。
