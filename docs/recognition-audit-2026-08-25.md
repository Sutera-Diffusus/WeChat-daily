# 微语识别算法拟真审核报告

日期：2026-08-25  
范围：噪音分层、信息筛选、并行话题、跨会话事件、严格待办、群内梗候选

> [!WARNING]
> **历史证据，结论已降级。** 本报告只证明 52 条人工构造样本上的局部规则和留存不变量曾按预期运行，不证明当前真实消息上的事件识别、跨会话合并、人物归因、标题摘要或最终首页展示正确。2026-08-26 的端到端复盘发现：候选聚类过宽、标题规则泛化、首页来源/`sameTopic` 二次合并以及 `detail_points` 继续渲染会共同放大错误。本文中的 precision/recall、证据绑定和“回归通过”不得作为生产上线或问题已修复的验收依据。
>
> 当前权威设计以 [design-review.md](D:/Project_Codex/Project_WeChatMoreFunction/docs/design-review.md) 第三版为准。后续必须使用脱敏真实金标准，分别评测 `message → mention → claim → event → topic_family → trend → presentation`，并完成固定输入到 API、DOM、截图和原始证据的端到端审核。本报告保留为 legacy A 基线的历史材料，不回写其当时的实验数字。

## 结论先行

这次不是只看单元测试，而是用一组人工预先标注的混合聊天做了当时链路的拟真审核。该样本表明局部规则在构造数据上能够回答三件事：哪些内容可以收起、哪些内容值得保留、哪些重复表达足以成为“梗候选”；“稳定”只适用于这组固定样本，不适用于真实消息或当前最终界面。

在这组拟真样本上，硬噪音和梗候选都达到 precision / recall 1.000；第一屏聚焦结果 precision 1.000、recall 0.805；把低优先级小事项也纳入完整编辑面后，precision 0.911、recall 1.000。这个结果说明算法适合先减少注意力消耗，再保留可回看的信息发散面，但不能把拟真样本的数字当成真实用户数据上的产品准确率。

本轮逐项处理后，legacy 输出增加了四类可检查字段：显式回复/引用链（包括跨长时间的“挖坟回复”）、表达清晰度状态、同义/别名归一依据，以及主题族与子主题。这些字段存在不等于事件边界、人物归因或展示链路已经正确；无法确认时输出 `context_needed` 或未分类统计的保守原则继续保留。

## “由多变少”可逆漏斗

这次把“先全量采集，再逐层收敛”固化成算法契约，而不是只作为产品口号：

1. 输入消息先全部进入识别池，每条消息都有稳定的 `row_id`；源端缺少 `message_id` 时使用采集顺序生成 `row:<index>`。
2. 识别池完成噪音、上下文、表达状态和候选角色判断；此阶段不因低价值而删除消息。
3. 消息再按唯一层级分流：`first_screen`、`suppressed_noise`、`context_pending`、`event_archive`、`dynamic_archive`、`low_value_archive`、`unclassified_archive`。
4. 第一屏只是可见性结果，收起原因、识别状态、主题标签、事件/动态证据链和原文片段都留在 `retention_ledger` 中，可回看、可复核、可重新聚合。

本次 52 条拟真消息的漏斗结果是：52 条进入原始层，52 条完成识别，45 条进入语义池，34 条进入编辑第一屏；台账仍保留 52 条，缺失 0、额外 0、重复 0，`all_rows_retained = true`。这说明“由多变少”目前是减少注意力占用，而不是不可逆地删消息。34 条是编辑第一屏口径；前面的 33 条 focus 指标仍按更保守的“动作、发现、事件证据”口径统计，便于与历史审核结果比较。

接口输出：`result["retention_ledger"]` 保存逐消息去向，`result["funnel"]` 保存阶段计数、层级计数和不变量校验；`summary.all_rows_retained` 与 `quality.retention_invariant_passed` 可直接作为自动审核门槛。

## 细节保真层：简报变短，但证据不变薄

本轮复核发现，原先的问题不只是摘要字数少，而是“主题简报只取少量证据 + 事件只取首尾消息 + 页面只展示一句总结”叠加造成的细节丢失。现在把可发布的判断和可回看的细节拆成两层：

- 主题和事件继续负责由多变少；`detail` 另外保存涉及对象、流程节点、平台限制、失败分支、影响范围、待核实项、源消息 ID 和带会话/发言人/时间的折叠时间线。
- 细节召回范围比“有效判断”更宽：上下文片段和低分但能解释平台、流程或失败分支的消息可以进入证据层，但不会因此被重复计入有效消息数或升级成新的待办。
- 主题同时输出 `participants`、`sender_names`、`speaker_points` 和结构化 `attributions`，默认显示“谁在什么会话提到什么”；署名摘要按实体、限制、失败、影响和流程证据排序，避免只因碰到一个泛词就把旁支发言认作核心观点。
- 页面默认仍保持收敛，只在主题或事件下展开细节；展开提示区分“当前展示条数”和“关联证据总数”，避免把 32 条预览误解成完整证据量。
- 原文证据保留上限为每个主题 256 个源消息 ID、折叠时间线预览 32 条；超过预览上限时，界面明确提示总数，后续可以继续接入按 ID 分页回看。

用用户给出的 GitHub 死循环构造拟真样本后，结果保留了 3/3 条源消息，并完整抽出 `GitHub`、`Linux.do`、`V2EX`、`linuxsb`、`QQ邮箱`，同时分别记录“老号登录/邮箱限制”“重新注册提示已注册”“重置密码收不到邮件”“可能错失技术情报”和待核实边界。也就是说，简报可以保持短，但不会再把 Linux.do、V2EX、linuxsb 等决定性上下文藏在原文之外。

对当前库中 2026-08-24 的真实分析结果，系统读取到 687 条消息，发布 8 个具体主题，另存 2 个未分类桶；其中“账号与平台”主题关联 4 条有效判断和 12 条可回看证据。当前这一天的已采集文本中没有用户示例的完整 GitHub 讨论，因此该例的 3/3 结果是拟真回归验证，不冒充真实历史命中。

## 审核样本与人工标签

样本包含 52 条消息、6 个会话，故意混入容易误判的内容：

- 项目反馈：不想看什么、信息茧房、跨群归档、群聊总结差异、会议录音质量、发言人和噪音。
- 并行话题：模型部署报错、选课截止时间、无对象的“请确认一下”、带对象的“是哪个接口”。
- 风控讨论：只读分析、同步频率、封号风险、本地读取、不自动发消息。
- 噪音：哈哈、笑死、收到、早上好、图片占位符和家庭闲聊。
- 梗样本：`未来古法` 与 `未来古法，低效，也许也是很好的买点`，各自带一条邻近反应。
- 反例：重复的“请明天确认报价”，用于验证操作性重复不会被误报成梗。

人工标签把“严格待办”和“需要回看/决策”分开。只读、同步频率和本地读取是风险或方案判断，不应被误压成普通待办；明确重复报价请求才进入严格待办队列。

## 梗候选识别是怎么做的

当前实现是“证据候选”，不是梗义解释器：

1. 先对文本做空格、标点、链接和媒体占位符归一化，识别完整短语的重复。
2. 再提取 4–8 字的保守短语锚点，用于覆盖“未来古法”和“未来古法，低效”这种自然变体。聊天胶水词、平台词、主题泛词和常见确认语会被排除。
3. 候选必须发生在同一个会话中，并满足重复门槛。普通操作请求、风险、交易和问题类文本，除非有至少两条邻近群内反应，否则不会进入梗候选。
4. 反应只绑定到反应前 5 分钟内最近的一次候选出现；中间如果插入了另一条实质消息，就否决这条反应绑定，避免把无关的“哈哈”算到梗上。
5. 候选会记录短语、匹配模式、出现次数、参与人数、反应次数、原消息 ID、反应消息 ID、置信度和不确定性。系统只说“梗候选”，不自行解释来源、指代和群体共识。

审核产出：

```text
未来古法
kind: inside_joke
occurrences: 2
participants: 2
reactions: 2
occurrence messages: meme-1, meme-2
reaction messages: meme-r1, meme-r2
```

“复古路线”没有被强行合并为同一个梗，只在相邻讨论的小事项中保留。这是有意的保守策略：语义上可能有关，但没有足够的重复和回应证据，自动合并会比漏报更容易制造错误解释。

## 审核结果

| 检查项 | 结果 | 解读 |
| --- | --- | --- |
| 硬噪音识别 | 7/7，precision 1.000，recall 1.000 | 反应、确认、寒暄、媒体占位符没有进入价值面；原始消息仍计入总量 |
| 严格待办 | 2/2，precision 1.000，recall 1.000 | 只保留明确对象和动作的重复报价请求 |
| 风险/决策回看覆盖 | 5/5 | 选课提醒、只读方案、同步频率和本地读取没有丢失，但留在事件/小事项回看面 |
| 第一屏聚焦面 | precision 1.000，recall 0.805 | 33 条聚焦产出全部命中人工价值标签，但 8 条低优先级内容没有挤进第一屏 |
| 完整编辑面 | precision 0.911，recall 1.000 | 45 条可回看产出覆盖全部 41 条人工价值消息；额外 4 条是家庭闲聊和无对象上下文片段 |
| 梗候选 | 1 个，precision 1.000，recall 1.000 | 正确识别 `未来古法`，没有把重复确认或重复报价当梗 |
| 可逆漏斗完整性 | 52/52 条进入留存台账，缺失 0、额外 0、重复 0 | 第一屏、噪音收起和归档都是可见性层，不构成原始消息删除 |
| 并行话题串线 | 0 条动态混入 | 模型部署与选课没有合并；“是哪个接口”回指模型消息，没有导入选课消息 |
| 风控重复事件 | 2 张重复卡合并为 1 张 | 一条事件保留项目群、私聊和风控群的证据链 |
| 跨长时间回复 | 新增回归通过 | 带 `reply_to_message_id` 的消息可恢复旧线程，并标记为“挖坟回复”，不会把中间无关主题带入 |
| 含糊表达 | 新增回归通过 | “请确认一下”不会因共享“确认”动词而升级；“这个接口要怎么处理？”只有在接口上下文存在时才进入待回看 |
| 同义/别名归并 | 新增回归通过 | “只读、同步频率、被检测、封号”可归入同一风控事件，并在 `cluster_quality.canonical_terms` 留痕 |
| 主题分类 | 主题泛类不再发布 | 低信息“其他讨论”保留为未分类计数，不生成用户可见话题简报；具体主题另有 `subtopics` |

完整编辑面中的 4 条额外消息不是硬噪音泄漏：家庭闲聊按照现有“社交信息可回看”契约保留；无对象的“请确认一下”被标成 `context_needed`，保留原文但不升级为待办。这正是“第一屏收敛、完整面可回看”的两层设计。

## 产出是否有价值

有价值，但价值主要体现在“降低必须阅读的内容”，而不是把所有聊天自动变成结论：

- 第一屏只留下明确事件、梗候选、严格待办和高信息发现，拟真审核中没有硬噪音误入。
- 跨会话风控被整理成一条证据链，能直接支持“只读、本地、低频同步”的使用规则讨论；同时保留“这不是安全保证”的不确定性。
- 群聊总结差异被单独识别为“产品差异”，没有和普通日报、周报混成同一类输出。
- 会议录音质量、转写、发言人和并行噪音仍作为产品反馈保留，避免只看到“模型部署”这类更容易识别的技术词。
- 梗不会只因为一句有趣的话就被宣布成立；用户可以根据证据回看并人工确认，后续反馈才有机会反哺阈值。

## 当前限制与下一步

这份报告是“拟真审核”，不是对真实微信历史消息的抽样统计。尤其需要真实脱敏数据继续验证：

- 反讽、谐音、图片梗、表情包、跨天复用和只有一个人知道的群内黑话，目前不能可靠解释梗义。
- 梗候选使用保守 lexical anchor；真正的同义改写可能漏报，当前宁可不把“复古路线”误认成同一个梗。
- 社交闲聊和上下文片段仍在完整回看面存在，可进一步做用户可配置的“硬收起 / 保留关系动态”策略。
- 会议录音还没有进入可靠识别闭环，录音质量、转写错误、错别字和发言人分离应单独建评测集。
- 下一轮应采集脱敏真实样本，人工记录五类反馈：有价值、误报、错误合并、漏报、梗义不确定；至少按会话类型、消息长度、是否有回应和是否跨会话分层计算指标。
- 当前主题分类在拟真样本中输出 8 个具体主题、3 条未分类低信息消息；这不是“分类已经正确”的证明，仍需用真实样本检查主题族是否过宽、是否把不同产品问题合并。
